You are a senior software architect and product engineer.

I want to design and build a developer-first CLI tool called KirokuForge.

KirokuForge is a local-first, Git-native AI knowledge assistant that converts AI-assisted project conversations into structured, reviewed, versioned Markdown documentation.

The product must NOT save or push raw conversations. Its purpose is not to archive chats, but to transform useful conversation outcomes into curated project knowledge.

Core concept:
- The user works with an AI assistant inside the CLI.
- The assistant helps reason about a project.
- When the user decides to save the useful outcome, KirokuForge generates a structured summary.
- The user reviews/edits the summary.
- KirokuForge writes the approved knowledge into Markdown files.
- The files are stored in a Git repository.
- The Git repository becomes the source of truth for project knowledge.

Product name:
- Product: KirokuForge
- CLI binary: kiroku
- Standard knowledge repository name: kirokuforge-knowledge

Meaning:
- “Kiroku” comes from Japanese 記録, meaning record/documentation.
- “Forge” represents the act of shaping raw conversation into structured knowledge.

Main positioning:
KirokuForge turns AI conversations into versioned project knowledge.

Tagline:

Repository model:
- KirokuForge uses one standard Git repository named `kirokuforge-knowledge`.
- This repository contains all projects.
- Each project is stored as a subdirectory.
- The repository is provider-agnostic.
- It must work with GitHub, GitLab, Gitea, Bitbucket or any Git server supported by standard Git remote URLs.
- KirokuForge must use pure Git operations for clone, fetch, pull, commit and push.
- It should not depend on GitHub CLI for the core workflow.

Repository initialization behavior:
- When the user runs `kiroku init`, KirokuForge should ask for a remote Git URL or allow local-only mode.
- The expected remote repository name is `kirokuforge-knowledge`.
- KirokuForge checks if the remote repository is reachable using pure Git, for example `git ls-remote <remote-url>`.
- If the repository is reachable, KirokuForge clones it.
- If the repository is not reachable, KirokuForge must not assume the reason. It should say: “Repository not found or inaccessible.”
- KirokuForge then asks the user to create a repository named `kirokuforge-knowledge` manually on their Git provider.
- After the user confirms creation, KirokuForge checks the remote again.
- If the remote is now reachable, KirokuForge clones it.
- If the repository is empty or does not contain `kirokuforge.yml`, KirokuForge asks whether to initialize the KirokuForge structure.
- If confirmed, it creates the base structure, commits it and pushes it.

Git workflow:
- Use Git CLI as the primary implementation because it respects the user’s existing SSH configuration, SSH agent and credential helpers.
- JGit can be used only as a secondary utility for status/diff/parsing if useful.
- Git operations must be provider-agnostic.
- Git supports common transport protocols such as Local, HTTP/HTTPS, SSH and Git protocol, so using Git directly allows the tool to work across multiple providers.
- `git clone` should be used to clone existing repositories.
- `git ls-remote` should be used to check remote reachability.
- Before writing knowledge, KirokuForge must pull/rebase from origin/main.
- Before pushing, KirokuForge must check the working tree status.
- The tool should never silently overwrite remote content.

Required Git commands:

- git clone <remote-url> <local-path>
- git fetch origin
- git pull --rebase origin main
- git status --porcelain
- git diff
- git add <files>
- git commit -m "<message>"
- git push origin main

Conflict resolution:
- If Git detects a merge conflict, KirokuForge enters an interactive conflict resolution flow.
- The AI may analyze the local version, remote version and base version.
- The AI may propose a reconciled version.
- The user must review and approve/edit the result.
- KirokuForge must not silently resolve semantic conflicts.
- Human-in-the-loop resolution is mandatory for conflicts.
- The user must be able to:
  1. view local version
  2. view remote version
  3. view AI suggestion
  4. manually edit final version
  5. accept AI suggestion
  6. abort the rebase/merge

# ADR-003 - Human-in-the-loop merge resolution

## Context
The system may face Git merge conflicts when multiple clients update the same project knowledge base.

## Decision
The system must not silently resolve semantic conflicts. It must involve the user.

## Consequences
- Safer knowledge base
- Slower conflict resolution
- Better trust

Summary generation:
The AI must transform a conversation into structured documentation.
The summary must:
- be concise
- be technical
- be readable by someone who did not see the original chat
- extract decisions, TODOs, open questions and technical notes
- avoid conversational noise
- avoid phrases such as “the user said” or “the assistant replied”
- avoid personal information unless explicitly relevant
- avoid saving raw chat content

Provider architecture:
Define an interface:

public interface LlmProvider {
    ProviderId id();
    AuthStatus authStatus();
    List<ModelDescriptor> listModels();
    LlmResponse complete(LlmRequest request);
    Stream<LlmChunk> stream(LlmRequest request);
}

Codex provider:
public final class CodexCliProvider implements LlmProvider {
    private final CodexCliClient codexCliClient;

    @Override
    public ProviderId id() {
        return ProviderId.of("openai-codex");
    }

    @Override
    public AuthStatus authStatus() {
        return codexCliClient.checkAuth();
    }

    @Override
    public LlmResponse complete(LlmRequest request) {
        return codexCliClient.runPrompt(request);
    }
}
