You are a senior software architect, Java engineer, and open-source developer tools product designer.

I want to design and build the first working open-source version of a CLI tool called KirokuForge.

KirokuForge is a local-first, Git-native, developer-first CLI that turns AI-assisted work sessions into structured, reviewed, versioned Markdown project knowledge.

The CLI binary name is:

kiroku

The standard knowledge repository name is:

kirokuforge-knowledge

The first open-source version must be fully functional as a local CLI. It must not require a SaaS backend.

Core product idea:
KirokuForge lets developers chat with an AI assistant, process the useful outcome of the session through a dedicated Knowledge Processing Agent, review the generated knowledge artifacts, and save them as Markdown files into a Git repository.

The Git repository is the published source of truth for project knowledge.

KirokuForge must never commit raw conversations.
Only reviewed, structured knowledge artifacts can be written to Git.

The basic flow is:

User starts a project session
→ user works with AI
→ user runs /save or kiroku save
→ Knowledge Processing Agent extracts useful knowledge
→ KirokuForge proposes Markdown artifacts
→ user reviews/edits them
→ KirokuForge pulls latest main
→ KirokuForge writes files
→ KirokuForge shows diff
→ user confirms
→ KirokuForge commits
→ KirokuForge pushes

Main architecture:

KirokuForge CLI
→ Chat Assistant
→ Session Context
→ Knowledge Processing Agent
→ Summary Candidate
→ User Review
→ Markdown Artifact
→ Git Sync Engine
→ kirokuforge-knowledge repository

Important distinction:
There are two AI roles.

1. Chat Assistant
The assistant used during the interactive session.
It helps the user reason, write, design, debug and analyze.

2. Knowledge Processing Agent
A dedicated post-processing agent.
It transforms the session into durable project knowledge.

The Knowledge Processing Agent is not the same as the Chat Assistant.

The Knowledge Processing Agent must:
- extract durable knowledge from the session
- ignore conversational noise
- extract decisions
- extract TODOs
- extract open questions
- extract alternatives considered
- extract architecture notes
- classify artifact types
- route content to target files
- generate Markdown
- propose commit messages
- validate that raw conversation is not being saved
- prepare a Summary Candidate for user review

The Knowledge Processing Agent must not:
- commit directly
- push directly
- silently overwrite files
- save raw conversation
- invent decisions
- resolve semantic conflicts without the user

Git rules:
- Use pure Git CLI operations as the primary implementation.
- Do not depend on GitHub CLI.
- Do not depend on a SaaS backend.
- The Git workflow must be provider-agnostic.
- It must work with GitHub, GitLab, Gitea, Bitbucket or any Git remote supported by Git.
- Use the user’s local Git, SSH agent and credential helpers.
- Use `git ls-remote <remote-url>` to check remote reachability.
- If the remote is not reachable, say: “Repository not found or inaccessible.”
- Do not assume whether the repo does not exist, permissions are missing, SSH is broken, or the network is down.
- If the remote is unreachable, ask the user to manually create a repository named `kirokuforge-knowledge` on their Git provider.
- After user confirmation, re-check with `git ls-remote`.
- If reachable, clone it.
- If the repo is empty or missing `kirokuforge.yml`, ask whether to initialize the KirokuForge structure.
- Before every write, run pull/rebase from origin/main.
- Never silently overwrite remote content.
- If conflict occurs, enter interactive conflict resolution.

Command behavior:

1. kiroku init
Initializes KirokuForge locally.

Flow:
- Create local config directory.
- Ask if user wants remote Git mode or local-only mode.
- If remote Git mode:
  - Ask remote URL.
  - Check remote with `git ls-remote`.
  - If unreachable:
    - tell user to create repo named `kirokuforge-knowledge`
    - wait for confirmation
    - retry `git ls-remote`
  - If reachable:
    - clone into configured local path
  - If missing `kirokuforge.yml`:
    - ask to initialize KirokuForge structure
    - create README.md, kirokuforge.yml, projects/, templates/
    - commit and push initial structure
- If local-only mode:
  - create local Git repository
  - initialize KirokuForge structure
  - do not require remote

2. kiroku repo status
Shows:
- local repo path
- remote URL
- current branch
- whether repo is clean
- whether local branch is ahead/behind origin/main
- whether kirokuforge.yml is valid

3. kiroku sync
Runs:
- git fetch origin
- git pull --rebase origin main
If conflicts occur:
- stop
- report conflicted files
- tell user to run `kiroku conflict resolve`

4. kiroku project create <project-name>
Creates:
projects/<project-slug>/
├── overview.md
├── architecture/
├── decisions/
├── notes/
├── open-questions/
└── todo/

Then:
- git add generated files
- commit with:
  docs(<project-slug>): initialize project knowledge base
- push if remote mode is enabled

5. kiroku project list
Lists available projects under projects/.

6. kiroku chat <project-name>
Starts interactive chat session.

Inside chat support slash commands:
- /save
- /diff
- /sync
- /project
- /exit
- /help

The session may be kept locally as temporary runtime/session state, but raw conversations must never be pushed to Git.

7. kiroku save <project-name>
Processes the current or selected session.

Flow:
- load session context
- load project context
- load existing knowledge tree
- run Knowledge Processing Agent
- produce Summary Candidate
- show generated artifacts
- ask user to review
- allow edit/regenerate/discard
- validate artifacts
- pull/rebase origin/main
- write approved Markdown files
- show git diff
- ask confirmation
- commit
- push

8. kiroku diff [project-name]
Shows current Git diff for generated artifacts.

9. kiroku conflict list
Shows conflicted files.

10. kiroku conflict resolve
Interactive conflict resolution.

Flow:
- list conflicted files
- for each file:
  - show local version
  - show remote version
  - optionally generate AI merge suggestion
  - allow user to accept/edit/abort
- after resolution:
  - git add resolved files
  - continue rebase or create conflict resolution commit
  - push

11. kiroku auth login
Configures LLM providers.

MVP providers:
- openai-codex
- openai-api
- ollama

Provider requirements:
A. openai-codex
- Uses official Codex CLI integration.
- Used when the user has ChatGPT subscription but no OpenAI API key.
- KirokuForge must not scrape ChatGPT.
- KirokuForge must not steal browser cookies.
- KirokuForge must not read undocumented private token files.
- It should delegate authentication and model access to official Codex CLI flows.

B. openai-api
- Uses OpenAI API key.
- Optional.

C. ollama
- Uses local Ollama server.
- No cloud login required.

12. kiroku auth list
Shows configured providers and auth status.

13. kiroku models list
Lists available models for configured providers if possible.

14. kiroku models use <provider:model>
Sets default model.

Knowledge Processing Agent prompt rules:
The agent must follow these rules:
- Do not preserve raw conversation.
- Do not write “the user said” or “the assistant replied”.
- Extract only durable project knowledge.
- Prefer concise technical documentation.
- Preserve decisions, tradeoffs, TODOs and open questions.
- If information is uncertain, put it under Open Questions.
- Never invent decisions.
- Never expose secrets, API keys, tokens or private credentials.
- Route each artifact to the correct project folder.
- Output must be structured and machine-parseable.

Default Markdown artifact format:

---
project: <project-slug>
type: <architecture|decision|note|todo|open-question>
status: draft
created_at: <yyyy-mm-dd>
updated_at: <yyyy-mm-dd>
tags:
  - <tag>
---

# <Title>

## Summary

## Key Points

## Decisions

## Alternatives Considered

## Open Questions

## TODO

## Related Files

Validation rules:
- target path must be under projects/<project-slug>/
- raw conversation phrases must be rejected
- API keys/secrets must be redacted
- required frontmatter must exist
- required sections must exist
- no file write without user approval
- no commit without user approval
- no push if working tree has unresolved conflicts
